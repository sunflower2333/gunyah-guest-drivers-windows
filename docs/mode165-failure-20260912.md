# 3040x1904 at 165 Hz failure investigation

The installed signed58471 driver enumerates the host's 3040x1904 at 165 Hz
timing but the observed mode switch returned `DISP_CHANGE_FAILED`. DWM then
reported `MILERR_NO_HARDWARE_DEVICE` and Windows lost the active display
topology. The target runtime failure is not yet fixed by this checkpoint.

The exact installed SYS and PDB resolve first reset caller RVA `0x184b8` to
`CompletePagingBufferOperation`; the ARM64 call at `0x184b4` invokes
`RequestHardwareResetAtAnyIrql`. The first aperture failure was stage 19,
`STATUS_DEVICE_NOT_READY`, detail zero: standard 2D resource destruction during
unmap returned `NotSubmitted`, with no release of backing ownership. This
precedes resource UNREF submission. Possible gates include runtime operation
admission, reset-state reconciliation, synchronous queue admission/mutex wait,
command allocation or pre-submit queue rejection. A submitted UNREF timeout
would produce `Unknown` with detail `0x30`; it is not the observed detail zero.
The separately preserved poison caller RVA `0x63cc` resolves to
`CtrlQueue::SubmitSynchronousLocked` at queue.cpp:851/852: a submitted command
failed its five-second completion wait. The preceding instruction at `0x63c8`
calls `PoisonSynchronousRequests`. This establishes the failure chain from a
control request timeout through the later refused UNREF and paging reset. The
timed-out command type is not captured by the existing poison triple, so the
specific request/host cause remains unresolved. Ownership and failure semantics
remain unchanged here.

The registry keys `NativeSynchronousEpochState`, `NativeSynchronousEpochGeneration`
and `NativeSynchronousPoisonCallerRva` are written only when native context
cleanup fails; they are not cleared at startup. They can survive a healthy new
boot and must not be presented as live queue state. Root observed a subsequent
boot with zero new aperture failures/reset, correct RGB and 764 GDI paints in
ten seconds, despite the old registry poison triple remaining present.

The advertised clock of 1,160,680,000 Hz and totals 3600x1954 are representable
by the current signal builder and reduced rational helpers. Same-resolution
refresh commits do not recreate the framebuffer. No source evidence currently
identifies an integer overflow as the observed cause.

The independent `CommitVidPn` defect fixed in this checkpoint is that Windows
may supply `AffectedVidPnSourceId=D3DDDI_ID_ALL` for a complete VidPN transaction,
but the driver previously passed that sentinel into per-source callbacks.
For this fixed one-source, one-target adapter, a whole transaction now resolves
to source zero. Invalid explicit source IDs fail before invoking OS callbacks.
A compile-time assertion requires revisiting this normalization before adding
multiple sources or targets. See Microsoft's
[DXGKARG_COMMITVIDPN contract](https://learn.microsoft.com/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgkarg_commitvidpn).

`NativeDisplayCommitStatus` previously read a counter with no writer, so its
zero value did not establish successful commits. The callback now publishes
pending on entry and its actual result on exit. `NativeDisplayIsSupportedRejects`
is also unwritten in the earlier source and is not evidence of no rejections;
this change does not alter that separate callback.

The standalone `.install_scripts/viogpu-test-display-mode.ps1` defaults to
`CDS_TEST`. It logs TEST/APPLY/SAVE/RESTORE, flags, result, monotonic elapsed time
and the current mode after each call. `-Apply` is required to change the mode,
and `-Keep` additionally saves a successful selection. It only selects an
enumerated mode. The root agent owns all target execution and recovery.

`viogpu/tests/vidpn-commit/run.py` exercises the actual production callback with
controlled OS peers and an omission negative control. Passing it does not prove
that the target paging refusal or the 165 Hz mode change has been repaired.

The companion instrumentation retains the first submitted completion-wait
failure for the lifetime of the control queue object, including across transport
teardown and re-enable. It does not record mutex admission failures, rejected
submissions, successful waits or completion epoch mismatches. A three-state
publication guard makes a partial record unreadable and the completed record
immutable. The existing five-second wait, poisoning, descriptor quarantine and
failure return values remain unchanged; no allocation or extra wait is added.

The existing failed-context-cleanup registry writer publishes:

| Key suffix after `NativeSynchronousTimeout` | Meaning |
| --- | --- |
| `Valid` | 1 only after all eight fields have been written; 0 means no usable snapshot |
| `Flags` | Bit 0 validates Type/ContextId; bit 1 validates ResourceId |
| `Type` | Virtio control command type, from a complete command header |
| `ContextId` | Context from that header |
| `ResourceId` | Resource from a complete, recognized fixed command only |
| `WaitStatus` | Exact completion wait NTSTATUS, including STATUS_TIMEOUT 0x102 |
| `CallerRva` | Direct caller of the noinline three-argument SubmitSynchronousLocked, relative to the matching SYS image |
| `CommandBytes` | Owned fixed command buffer length; separate data and response buffers are not read |
| `EpochGeneration` | Submission epoch before poisoning, which can differ from the later poison triple |

Only known resource create/unref/scanout/flush/transfer/backing/blob commands
decode a resource. SUBMIT_3D lengths, unknown payloads and truncated fixed
commands never become guessed resource IDs. Resource zero is valid when bit 1
is set (for example, disable scanout).

All these registry values remain historical failure telemetry and can survive
a new boot. Capture the full before/after key set with driver identity and
fresh paging/reset counters; do not infer a current timeout merely from Valid=1.
If an earlier timeout occurred in the same queue lifetime, its first record
intentionally survives later failures. No new host/UMD ABI is introduced.
